# leurs v2 plan

leurs v2 is a rewrite of the bot in TypeScript, with SQLite instead of JSON files. The Python code
stays in the repo as a reference for how each feature behaves until the cutover, then it is deleted.

Work happens on the `v2` branch. Each phase below is one or more PRs into `v2`, and `v2` merges into
`main` at cutover.

## Decisions

| Topic               | Decision                                                                                                                            |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Language            | TypeScript on Node 22 LTS, discord.js v14                                                                                           |
| Storage             | SQLite through Drizzle ORM. Existing JSON data is imported once                                                                     |
| Commands            | Every command works as a slash command and with the server's prefix (default `-`). Old command names keep working as prefix aliases |
| Name                | leurs                                                                                                                               |
| Economy             | Kept, with jobs and gambling. Wallet and bank merge into one balance, so `deposit` and `withdraw` go away                           |
| In-jokes            | Kept, except `hwmo`                                                                                                                 |
| Translation         | Done through DeepSeek, sharing the AI client and quota                                                                              |
| Language of the bot | English. In-jokes stay as they are                                                                                                  |

## Stack

- Node 22 LTS, pnpm, TypeScript
- discord.js v14 with our own command framework (see below)
- `better-sqlite3` and Drizzle ORM, migrations generated by `drizzle-kit`
- `zod` for config, `pino` for logs, built-in `fetch` with `AbortSignal.timeout()` for HTTP
- `@napi-rs/canvas` for the quote image
- Vitest for tests
- Docker: multi-stage build, non-root user, `data/` on a volume

## Code rules

The base must stay easy to maintain, so the tooling enforces the rules instead of reviewers.

### TypeScript

`strict: true`, plus `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`,
`noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals`, `noUnusedParameters`,
`verbatimModuleSyntax` and `"module": "NodeNext"`.

### Lint and format

- ESLint with typescript-eslint `strictTypeChecked` and `stylisticTypeChecked`. Key rules:
  `no-floating-promises`, `no-misused-promises`, `switch-exhaustiveness-check`, `no-explicit-any`,
  `no-non-null-assertion`, `no-unsafe-*`.
- `eslint-plugin-import` for ordering and no import cycles, and a curated subset of `unicorn`.
- `no-restricted-imports` enforces the layer rules below.
- CI runs `eslint --max-warnings 0`.
- Prettier with default settings.
- Knip reports unused files, exports and dependencies.
- lefthook runs lint, format and typecheck on staged files before each commit.
- commitlint enforces conventional commits.
- Renovate keeps dependencies updated.
- `main` and `v2` are protected: CI must pass and one review is required.

### Layers

```
commands/, events/  ->  services/  ->  db/
          \                /
           ->   ui/, lib/
```

- `commands/` and `events/` handle Discord only: read options, call a service, reply. They cannot
  import `db/`.
- `services/` holds the logic and is the only layer that touches the database. It cannot import
  `discord.js`, so it is tested with Vitest and an in-memory SQLite database.
- `ui/` holds the embed helpers and the paginator. Every reply goes through it.

## Command framework

Each command is defined once. The framework builds the slash command and the prefix parser from the
same definition, and the handler does not know which one called it.

```ts
export default defineCommand({
  name: "jobs",
  description: "Browse and manage your jobs",
  subcommands: {
    buy: {
      description: "Buy a job",
      options: { job: opt.string({ autocomplete: jobNames }) },
      prefixAliases: ["buyjob"],
      run: async (ctx, { job }) => ctx.reply(await jobs.buy(ctx.user.id, job)),
    },
  },
});
```

The handler gets a `ctx` with `user`, `guild`, `reply()`, `defer()` and `followUp()`.

Option types: user, member, role, channel, integer, number, string, rest-of-line text, choice,
boolean, duration (`30m`, `7d`, `perm`) and amount (`500`, `50%`, `all`). In prefix mode, users,
roles and channels resolve from a mention, an ID or a name.

| Feature                          | Slash                                                    | Prefix                                               |
| -------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- |
| Aliases                          | Not supported                                            | Every old command name is an alias                   |
| Private replies                  | Ephemeral                                                | Normal reply that deletes itself after a few seconds |
| Autocomplete                     | Yes                                                      | Fuzzy match on the typed value                       |
| Modals (`/embed`)                | Yes                                                      | Fields passed as arguments                           |
| Context menus (Quote, Translate) | Yes                                                      | Reply to a message with `.quote` or `.translate`     |
| Permissions                      | `permissions` field, admins can override in Integrations | Same `permissions` field, overrides are ignored      |

- The prefix is set per server with `/prefix`. Mentioning the bot also works as a prefix.
- Every command has an optional `cooldown`. A 3 second per-user cooldown applies to all commands
  except for admins. Cooldowns of an hour or more are stored in the database.
- Errors: `UserError` is shown to the user as a red embed. Anything else is logged with an ID and
  the user sees that ID.

## Database

Tables: `guild_settings`, `cooldowns`, `wallets`, `jobs`, `user_jobs`, `levels`, `lastfm_accounts`,
`birthdays`, `timezones`, `warnings`, `mod_actions`, `nickname_history`, `role_backups`,
`auto_reactions`, `reaction_roles`, `blocked_terms`, `scheduled_tasks`, `ai_usage`,
`typing_results`.

Tables with per-server data have a `guild_id` column. Snipe, AFK and pending typing challenges stay
in memory. SQLite runs in WAL mode.

`scripts/import-json.ts` reads these files from the old `data/` folder: `bank`, `jobs`, `levels`,
`voice_levels`, `lastfm`, `prefix`, `birthdays`, `timezones`, `timezone_preferences`, `warnings`,
`user_actions`, `nickname_history`, `saved_roles`, `auto_reactions`, `reaction_roles`,
`blockedterms`, `punishments`. Wallet and bank are added together into one balance.

## Operations

- Two bot applications: a dev bot on a test server and the prod bot, each with its own token.
- `pnpm deploy:commands` registers slash commands on the test server in development and on every
  server in production, and only uploads changed definitions.
- Gateway intents: Guilds, GuildMembers, GuildMessages, MessageContent, GuildVoiceStates,
  GuildMessageReactions. GuildMembers and MessageContent are privileged and need Discord
  verification once the bot is in 100 servers.
- Hosting: Docker Compose on the current server with `restart: unless-stopped`.
- Backups: nightly `sqlite3 .backup` copied off the server.
- Logs: pino to stdout.
- Docs: `scripts/gen-docs.ts` writes the command pages for docs.leurs.ch from the definitions.

## Team workflow

- One issue per command or feature, labelled by phase.
- A command is done when it works as slash and prefix, its old names work as aliases, its service
  has tests, its docs page is generated and it has been checked on the dev bot.
- A PR template with that checklist. CODEOWNERS on `src/core/`.

## Phases

1. **Foundation.** Tooling, CI, config, database, command framework and prefix parser, error
   handling, cooldowns, settings, scheduler, Docker, `/help`, `/about`, `/prefix`, `/settings`.
2. **Levels**, with the import for levels data. This is the reference the other phases copy.
3. **Economy, jobs and gambling**, with the import for bank and jobs data.
4. **Moderation.**
5. **Utility**, typing tests and fun.
6. **Integrations.**
7. **Cutover.** Import production data, run v2 on the test server, update docs.leurs.ch and the
   README, switch the token, delete the Python code, merge `v2` into `main`.

Phases 3 to 6 can run in parallel once phase 2 is merged.
